## 1. Purpose & scope

This document covers how analysis-ready `.npz` datasets are produced from raw driving footage, for the TFV6 primary agent. It spans the full chain:

1. **Route selection** — `unzip_routes.ps1` (Stage 1; absent from the repo, see §6) extracts a subset of LEAD CARLA leaderboard route zips.
2. **Migration to npz** — `migrate_lead_to_baseline.py` (Stage 2) discovers extracted routes, groups them by town, samples frames, remaps the navigation command, and writes one `.npz` per route into `baseline_data/`, `test_data/`, or `val_data/`.
3. **Loaders** — `BaselineDataLoader` / `BaselineComputer` (offline baseline computation) and `LabeledTestLoader` / `PerturbationApplier` (test/val labeling) consume those npz files and drive the ATOMs profile computation (Topic 4) and the perturbation labeling (Topic 6).

The split design — **why Town05 is the held-out test/val town**, the **canonical vs `alt_split` tradeoff**, and the **val-set auto-exclusion** — is the load-bearing methodological content here. Perturbation *application detail* (the 5-way mix, how each perturbation transforms pixels) belongs to Topic 6; it is referenced only as far as needed to describe how `*_labeled.npz` files are structured.

Scope note: the entire migration path is TFV6-specific (wide-only, no narrow camera, grouped semantics already collapsed in the source PNGs). WoR datasets are collected live in CARLA via `BaselineDataCollector`/`TestDataCollector` (§3.5) and never pass through `migrate_lead_to_baseline.py`.

## 2. Key design decisions

### 2.1 Source: the LEAD dataset instead of live collection

TFV6 driving footage originates from the **LEAD CARLA leaderboard dataset** (`ln2697/lead_carla` on HuggingFace), pre-downloaded to `D:\Carla_tfv6_data\`. The rationale (`docs/design_decisions.md:288-311`): the TFV6 model was trained on 4× L40S GPUs and runs at ~0.5 fps on CPU, so collecting tens of thousands of baseline frames live in CARLA is impractical. Only `noScenarios` routes are used for clean driving; scenario routes (accidents/obstacles) are not used at all (the OOD signal comes from synthetic perturbations, not from in-sim hazards — `docs/design_decisions.md:310-311`).

Consequence: the analysis never observes the live agent's exact inputs. LEAD frames are 3-camera 1152-wide JPEGs, whereas the live agent runs on 6-camera 2304-wide images — a systematic domain shift documented as findings 2.2/2.3 (Topic 2). Every dataset produced here inherits that mismatch.

### 2.2 Town05 as the held-out test/val town (canonical split)

The original ("canonical") split reserves **Town05** for the test and validation sets, and uses all other towns (Town03/04/06/07/10/15) for the baseline (`migrate_lead_to_baseline.py:357-358`, `migrate_testset:392-393`). Town05 is the only town withheld from training distribution in this design.

**Rationale / alternatives considered** (`docs/design_decisions.md:9-25, 621-625`):
- Town05 was chosen as the held-out town simply because it is one of the LEAD towns and is set aside entirely from baseline extraction.
- **Acknowledged downside:** test frames are OOD *by construction* — different road geometry and visual character — independent of any applied perturbation. A detector that merely recognises "novel town" scores well without detecting any perturbation. This confound is the explicit motivation for the alternative split (§2.3).
- The validation set uses **different Town05 routes** than the test set (§2.5), so val and test never share routes but share the same domain.

### 2.3 Canonical vs `alt_split` — what OOD signal each yields

`atoms_config.py:60-74` exposes `EXPERIMENT_VARIANT ∈ {"original", "alternative"}`. The two splits answer different questions:

| | Canonical (`original`) | Alternative (`alt_split`) |
|---|---|---|
| Baseline towns | all except Town05 | all towns (Town05 included) |
| Test/val town | Town05 only | random route slice of all towns |
| Split granularity | per-town, route-grouped | route-level, shuffled |
| Path resolution | `baseline_data` / `test_data` / `val_data` / `results` | `*_data_alt` / `results_alt` |
| OOD signal under test | domain shift **+** perturbation (confounded) | perturbation **only** (same distribution) |
| Generated by | `--mode baseline` / `testset` / `valset` | `--mode alt_split` |

The alternative split (`migrate_alt_split`, `:494-567`) pools all routes, shuffles them deterministically with `conf.RANDOM_SEED`, and slices at the **route level** into disjoint baseline/test/val sets. Because whole routes go to exactly one split, there is no temporal-correlation leakage between splits, and no filename overlap (`docs/design_decisions.md:639-643`). Since all three sets share the town distribution, any OOD signal must come from perturbations alone — eliminating the "novel town" confound at the cost of no longer testing genuine domain generalisation.

The **currently configured variant is `"alternative"`** (`atoms_config.py:63`), which means all live paths resolve to the `*_alt` directories — note this contradicts the path examples throughout `CLAUDE.md`'s Data Layout, which describe the non-`_alt` canonical layout (finding 5.7).

### 2.4 Even-spaced (deterministic stride) frame sampling

Within each retained town, all `(route, frame_idx)` pairs are flattened into one list and sub-sampled with a fixed stride (`build_sampling_plan:259-276`):

```python
frames_per_town = max(1, n_frames // len(active_towns))   # :259
step            = max(1, len(all_pairs) // frames_per_town) # :275
selected        = all_pairs[::step][:frames_per_town]       # :276
```

**Rationale:** even spacing across the concatenated route list gives temporally-decorrelated frames spread over the whole town's footage, rather than a contiguous block. Sampling is **fully deterministic but unseeded** — it depends only on the route discovery order (`discover_routes` uses `sorted(root.rglob("rgb"))`, `:120`) and the frame stride. No RNG is involved in canonical-mode sampling; reproducibility hinges on the on-disk route set being identical.

**Caveat:** because pairs are grouped by route consecutively before striding, a large `step` can skip whole short routes entirely, and the realised frame count is `≤ frames_per_town` (truncation at `[:frames_per_town]`). The target `n_frames` is therefore an upper bound, not an exact count (finding 5.2).

`alt_split` uses a sibling helper `_build_plan_from_routes` (`:409-432`) that strides over the *pre-assigned* route subset with no per-town balancing — `step = max(1, len(all_pairs) // n_frames)` (`:421`).

### 2.5 Val-set auto-exclusion (no manual exclusion list)

`migrate_valset` (`:439-487`) guarantees the val set never overlaps the test set by reading the test directory's npz stems and excluding those routes. The npz naming convention `run_<town>_<route_dir_name>` (`_write_plan:326`) is parsed back: for each `run_*.npz` in `conf.TEST_DATA_DIR/frames`, the `run_<town>_` prefix is stripped and the remainder (`route_dir.name`) added to an `exclude_routes` set (`:462-468`). That set is passed to `build_sampling_plan(..., exclude_routes=...)`, which drops matching route names within the retained towns (`:247-253`).

**Rationale** (`docs/design_decisions.md:9-32`): the val set exists purely for hyperparameter selection (k-NN k, GMM-kNN k, GMM cluster count K) so that those choices are not made on the test labels (data leakage). It must therefore be drawn from the same held-out town but **disjoint routes**. The auto-exclusion removes the need for a manually maintained route list. Edge case: the prefix-strip assumes exactly one leading `run_<town>_` token; route directory names that themselves embed the town string (LEAD names like `Town05_Rep0_Town05_ll_6_...`) survive correctly only because the *first* `run_Town05_` is stripped, not subsequent occurrences (works as intended, but brittle — finding 5.6).

### 2.6 Command remapping: 1-based RoadOption → 0-based index

LEAD meta stores `next_commands` as CARLA `RoadOption` integers (1-based). The analysis pipeline and the agent's planning-decoder conditioning expect a 0-based index. `_convert_command` (`:76-85`) applies a fixed table `_ROAD_OPTION_TO_IDX` (`:68`):

| RoadOption (LEAD, 1-based) | Name | → 0-based index |
|---|---|---|
| 1 | LEFT | 0 |
| 2 | RIGHT | 1 |
| 3 | STRAIGHT | 2 |
| 4 | LANEFOLLOW | 3 |
| 5 | CHANGELANELEFT | 4 |
| 6 | CHANGELANERIGHT | 5 |

`_convert_command` also accepts already-0-based values (`0 ≤ v ≤ 5` passthrough, `:82-83`) and `RoadOption` enum objects (`.value`, `:77-78`). Unknown values default to `3` (LANEFOLLOW) with a warning (`:84-85`). The per-frame source is `meta["next_commands"][0]`, the *next* upcoming option, with a list default of `[4]` (LANEFOLLOW → index 3) when absent (`load_frame:181`).

This mapping round-trips exactly with what `ATOMsCarla._make_minimal_data` reconstructs into a length-6 command one-hot (Topic 4 §8). Note the default-command inconsistency tracked as findings 1.7/2.12: the migration default and `_make_minimal_data` agree on `3 = LANEFOLLOW`, but the ATOMs pipeline passes `DEFAULT_CMD = 2` (STRAIGHT) with a "(FOLLOW_LANE)" comment — harmless here because every migrated frame carries a real `cmd`.

### 2.7 npz-per-route (not per-episode) and run_id semantics

Each town's sampling plan is regrouped by route, and one compressed npz is written per route (`_write_plan:305-342`), named `run_<town>_<route_dir.name>.npz`. The loaders assign `run_id` by *file enumeration order* after `sorted(...)` glob (`BaselineDataLoader.load_all_runs:364`, `dataset._load_all_runs:561`) — i.e. `run_id` is not stored in the frame npz; it is an index into the sorted file list at load time. This matters for trajectory matching (clean↔perturbed by `(run_id, frame_idx)`) and for the alignment-key guard in `run_analysis.py`.

## 3. Implementation details

### 3.1 The four migration modes (`migrate_lead_to_baseline.py`)

CLI dispatch at `:631-644`:

| `--mode` | Function | Source towns | Output dir | Default target |
|---|---|---|---|---|
| `baseline` | `migrate` `:351-367` | all minus `--exclude_towns` (default Town05) | `conf.BASELINE_DATA_DIR/frames` | `--n_frames 3000` |
| `testset` | `migrate_testset` `:374-402` | `--testset_towns` (default Town05) only | `conf.TEST_DATA_DIR/frames` | `--testset_n_frames 500` |
| `valset` | `migrate_valset` `:439-487` | `--testset_towns` (default Town05), minus test routes | `conf.VAL_DATA_DIR/frames` | `--testset_n_frames 500` |
| `both` | `migrate` then `migrate_testset` | — | both | — |
| `alt_split` | `migrate_alt_split` `:494-567` | all minus `--exclude_towns` (default none) | `_DATA_ROOT/{baseline,test,val}_data_alt/frames` | `--baseline_n 5000 / --test_n 1000 / --val_n 1000` |

Note: `valset` is dispatched on `args.testset_n_frames`/`args.testset_towns` (`:635-636`), reusing the test-set CLI args; there is no separate `--val_n` for canonical val (that flag is `alt_split`-only).

Shared pipeline for the first four modes:
1. `discover_routes(root)` (`:114-125`) — every subdir under `--lead_dir` containing `rgb/`, `semantics/`, and `metas/`; works flat or nested (`rglob("rgb")`).
2. `build_sampling_plan(routes, n_frames, exclude_towns, include_towns, exclude_routes)` (`:191-286`) — town detection, filtering, stride sampling (§2.4).
3. `_write_plan(plan, out_dir)` (`:293-344`) — loads frames and writes one npz per route.

`alt_split` bypasses `build_sampling_plan` and instead builds three plans via `_build_plan_from_routes` from a deterministic route-level shuffle (`:540-566`):
```python
rng      = np.random.default_rng(seed)                  # seed = conf.RANDOM_SEED, :500
order    = rng.permutation(len(filtered)).tolist()      # :541
i_test   = round(len(shuffled) * baseline_n / total)    # :545
i_val    = round(len(shuffled) * (baseline_n+test_n)/total)  # :546
```
The split fractions are derived from the *frame targets* (`baseline_n:test_n:val_n`) but applied to the *route count* — i.e. the route-level split is proportional to the requested frame budget, then frames are sampled from each route subset. `alt_split` **always writes to `_alt` directories regardless of `EXPERIMENT_VARIANT`** (`:557-564`, hardcoded under `_DATA_ROOT`), so the analysis only sees this data when `EXPERIMENT_VARIANT="alternative"` (finding 5.5).

### 3.2 Town detection (`_detect_town`, `:94-107`)

Two-stage: first scan meta keys (`town`, `map`, `world`, `map_name`, `carla_map`) for a substring match against `_KNOWN_TOWNS` (`:91-92`: Town01/02/03/04/05/06/07/10/15), then fall back to scanning the route directory path parts. Returns `None` → `"unknown"` bucket (`:227-228`). LEAD metas carry `town` directly (e.g. `"Town03"`).

### 3.3 Single-frame loading (`load_frame`, `:143-184`)

Per `(route_dir, frame_idx)`:
- **RGB** (`:159-165`): `cv2.imread(IMREAD_UNCHANGED)` → BGR→RGB → transpose to `[3, H, W]` `uint8` contiguous. Source JPEG is `(384, 1152, 3)` = 3 cameras × 384 px wide (header `:38`, `:150`).
- **Semantics** (`:167-174`): `cv2.imread(IMREAD_UNCHANGED)`; if 3-D, take **channel 0** (`:172-173`, where CARLA writes class IDs) → `[H, W]` `uint8`. These are LEAD grouped semantics (10 classes, `save_grouped_semantic=True`) per Topic 4 §6.
- **Meta** (`:71-74, 176-182`): XZ-compressed pickle (`lzma.decompress` + `pickle.loads`); extracts `speed` (float), `brake` (bool), and `next_commands[0]` → command. Returns `None` (frame skipped) if any of the three files is missing.

### 3.4 npz output schema (migration modes)

`_write_plan` (`:329-338`) and `migrate_alt_split` write **identical schema** (TFV6 wide-only):

| Key | Shape | dtype | Source |
|---|---|---|---|
| `wide_rgb` | `[N, 3, 384, 1152]` | `uint8` | concatenated 3-camera RGB |
| `seg_red_wide` | `[N, 384, 1152]` | `uint8` | grouped class IDs (channel 0) |
| `cmd` | `[N]` | `int32` | 0-based command (§2.6) |
| `speed` | `[N]` | `float32` | m/s |
| `is_brake` | `[N]` | `int8` | brake flag |
| `frame_idx` | `[N]` | `int32` | original LEAD frame index |

`narr_rgb` / `seg_red_narr` are **intentionally omitted** (header `:28-30`); the loaders return `None` for missing keys and `_make_minimal_data` handles the absence. The labeled-set schema (`test_labeled.npz`) adds `run_id`, `label`, `perturbation`, `intensity` and is produced downstream by `PerturbationApplier` / `prep_test.py` (§3.6, Topic 6).

### 3.5 Loaders

**`BaselineDataLoader`** (`baseline_dataset.py:291-410`):
- `load_run(path)` (`:314-332`) — single npz → dict; missing `narr_rgb`/`seg_red_narr` → `None`; `run_id` set to all-zeros.
- `load_all_runs(dir, pattern="run_*.npz", max_runs)` (`:334-389`) — sorted glob, concatenates all runs, assigns `run_id` by file order (`:376`), `None`-safe concat (`:383-387`).
- `summary(data)` (`:396-410`) — prints frame/run/resolution/command/speed stats.

**`BaselineComputer`** (`baseline_dataset.py:417-587`):
- `compute_and_save(cmd_filter, max_runs)` (`:443-587`) — loads all baseline frames, iterates per frame, calls `atoms.process_frame(wide, narr, seg_wide, seg_narr, cmd=cmd, spd=spd)` (`:518`) — **passes `spd`**, unlike the local test loop (finding 4.4). Stacks the per-frame profiles into `series [N, num_classes]`, computes `mean` and `cov`, and saves `baseline_{MODE_ANALYSIS}.npz` (`:440, :571-582`) with `series`/`mean`/`cov`/`class_ids`/`class_names`/`cmd_filter`/`n_frames`. An optional `cmd_filter` builds command-specific baselines (`:467-470`).
- A large block of `LRPTestSuite`/`ATOMsTestSuite`/`TFV6TestSuite`/diagnostics calls is **commented out** (`:476-496`) — dead test scaffolding (Topic 11).

**`LabeledTestLoader`** (`dataset.py:435-519`):
- `load(name="test_labeled")` / `load_val(name="val_labeled")` (`:450-458`) — resolve to `conf.TEST_DATA_DIR` / `conf.VAL_DATA_DIR`.
- `load_path(path)` (`:472-485`) — `np.load(..., allow_pickle=True)` (needed for the `perturbation` object array); `setdefault`s `narr_rgb`/`seg_red_narr` to `None` for TFV6.
- `load_live_pert(name)` (`:461-470`) — concatenates `live_pert_frames/run_<name>_live_pert_*.npz`.
- `split_by_perturbation(data)` (`:501-519`) — per-perturbation sub-dicts for the per-type breakdown (Topic 8 step 11).

**Online collectors (WoR live collection)** — `BaselineDataCollector` (`baseline_dataset.py:113-284`) and `TestDataCollector` (`dataset.py:107-206`) buffer frames during a CARLA episode, sampling every `sample_every`-th frame (`:193`, `:148`), and flush to npz when the buffer hits `MAX_BASELINE_SIZE`/`MAX_TEST_SIZE`/`MAX_LIVE_PERT_SIZE` (`:211`, `:163`). They write the same schema as the migration writer (wide+narrow when present). `sample_every` defaults to `conf.IMAGE_SAMPLE_INTERVAL` (baseline) / `conf.TEST_SAMPLE_INTERVAL` (test), wired in `image_agent.py:90-91` and `lbc_agent.py:112-113`. The TFV6 live-perturbation collector uses `conf.TEST_SAMPLE_INTERVAL` (`sensor_agent_live_perturbation.py:112`). These collectors are **not** used for the TFV6 LEAD-migrated datasets — only for WoR live data and TFV6 live-perturbation recordings (Topic 9).

### 3.6 Labeled-set construction (relevant to Topic 6)

Two parallel implementations build `*_labeled.npz` from clean frame npz files, **and they must produce the identical frame-to-entry assignment** (same seed + same 5-way spec → same shuffle):

- **Local:** `PerturbationApplier.apply(spec, seed=42, output_name)` (`dataset.py:238-409`). `_assign_frames` (`:411-428`) converts spec fractions to exact counts (last entry absorbs rounding, `:419-421`), builds a per-entry index array, and `rng.shuffle`s it under `np.random.default_rng(seed)`. For TFV6, `pgd` frames are **deferred** — labelled perturbed (`label=1`) but kept with clean pixels (the attack is crafted on HPC); emits a warning (`:300-312`).
- **HPC:** `hpc/prep_test.py` (`:85-93` `assign_frames`, identical algorithm) — model-free, applies image-space perturbations and defers `pgd` pixels to `compute_test_chunk.py`. The hardcoded `_SPEC` (`:35-42`) is the same 5-way 20% mix.

The 5-way 20% mix (`run_analysis.py:696-702`, `prep_test.py:35-42`): clean / `gaussian_noise` / `brightness_scale` / `camera_loss` / `pgd`. The val set reuses the **same prep path** against the val frames dir (`submit_val.sh:79-90` invokes `prep_test_task.sh`), producing `val_labeled.npz`. Detailed perturbation semantics → Topic 6.

## 5. Known limitations & open issues

- **`unzip_routes.ps1` absent from version control** (finding 1.8) — Stage 1 route selection (the top-N-largest-zips-per-town logic) exists only in `CLAUDE.md` prose. Which routes ended up in each split is therefore not reproducible from the repo; a new angle (finding 5.4) is that the *baseline/test/val membership* is doubly non-reproducible: even given the same extracted routes, canonical-mode frame sampling is unseeded (§2.4) — only `alt_split` is seeded.
- **Camera-count / resolution domain shift** (findings 2.2/2.3) — all migrated frames are 3-camera 1152-wide, the live agent uses 6-camera 2304-wide. Under the canonical Town05 split this compounds with town domain shift; the alt-split removes town shift but not camera shift. Acknowledge as a systematic confound in the thesis.
- **Canonical sampling determinism gap** (finding 5.2) — `n_frames` is an upper bound, not exact; the realised count depends on route discovery order and per-route lengths, and large strides can drop short routes entirely. No seed, no manifest of which frames were selected is written.
- **`EXPERIMENT_VARIANT` decoupled from `alt_split` output** (finding 5.5) — `migrate_alt_split` always writes `_alt` dirs, but the analysis reads them only when `EXPERIMENT_VARIANT="alternative"`. Running `alt_split` while the config still says `"original"` silently produces data that is never read (and vice versa, canonical data is ignored when the flag is `"alternative"`).
- **Segmentation-channel inconsistency between loaders** (finding 5.1) — `dataset._to_hw_uint8:544` slices channel **2** (blue) while `migrate`/`baseline_dataset` use channel **0**. For LEAD/CARLA semantic images R=G=B=class_id so the value is identical in practice, but the two implementations disagree and `baseline_dataset.py:96-98` explicitly documents that channel 2 is *wrong* in general (only correct for BGRA).
- **Val auto-exclusion brittleness** (finding 5.6) — the `run_<town>_` prefix strip (`migrate_valset:462-468`) assumes canonical naming; it would mis-handle `alt_split`-named files or any future naming change, silently failing to exclude.
- **`run_id` is positional, not stored** — assigned by sorted-file order at load time (`:364`, `:561`); inserting/removing a route file renumbers all subsequent runs, which can break clean↔perturbed `(run_id, frame_idx)` matching across recomputations.
- **Stale `docs/design_decisions.md:305-308`** — the `TODO_SHAPE`/`TODO_CMD`/`TODO_TOWN` placeholders ("remain until a sample file is inspected") are resolved in code (shape, command map, town key all implemented); the surrounding text still says (384, 2304, 3) "expected" while the code header confirms (384, 1152, 3) (finding 5.3).

Confirmed via `Glob **/*.ps1`: there are **no PowerShell scripts in the repository**. The script is described only in `CLAUDE.md` (Stage 1 of the Raw Data Creation Pipeline) and `docs/design_decisions.md:28`. Per that description it:

- reads per-route `.zip` files from `D:\Carla_tfv6_data\data\carla_leaderboard2\zip\noScenarios\`,
- groups zips by town, picks the **N largest by file size** per town (`-RoutesPerTown`),
- excludes towns via `-ExcludeTowns`,
- extracts to `...\data\noScenarios\<route_name>\` (each route → `rgb/`, `semantics/`, `metas/`).

This is finding 1.8 (already logged). The relevant downstream consequence for Topic 5 (new angle, finding 5.4): the extracted route set is the *only* input to `migrate_lead_to_baseline.py`, and since the migration's canonical sampling is itself unseeded, neither the route selection nor the frame selection is reproducible from version control.
